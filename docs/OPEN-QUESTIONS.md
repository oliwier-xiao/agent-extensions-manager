# Open decisions
Questions the research could not settle on its own, because the answer is a preference rather than a fact.
1. Claude skill toggles: should the panel write skillOverrides to ~/.claude/settings.json (global, affects every project) or to the repo-root .claude/settings.local.json (which is what Claude Code's own /skills UI writes)? Writing the wrong one means the panel and /skills silently disagree — and neither file currently contains the key, so we are creating it either way.
2. skillOverrides has four states (on / name-only / user-invocable-only / off), and 'name-only' is a real token saving that no other tool exposes. Should Space be a plain on/off, with the two middle states in the detail view — or should Space cycle all four?
3. Do MCP toggles ship in v1? There is NO CLI for enable/disable (claude mcp has only add/get/list/login/logout/remove), the toggle is per-project, and it means writing ~/.claude.json under a mkdir-based lock protocol we only know by decompiling one build. Deferring costs nothing in v1 since nothing else we need lives in that file.
4. For 'create once, use in N tools': is ~/.agents/skills the canonical authoring location? Codex reads it natively and OpenCode discovers it, but Claude Code has zero references to it — so Claude always needs a symlink or copy. Accepting that asymmetry (and never touching your existing symlinks) is the cheapest design.
5. For 'setup for a project': copy or symlink? Symlink keeps updates flowing from one source and is followed by all three tools; copy is committable and is what the impeccable plugin does (15 per-tool copies). Your machine currently has both patterns for the same skill (~/.claude/skills/omarchy is a copy that has drifted from the /usr/share original by one line — Claude reads your edit, OpenCode reads the original).
6. ~~Plugin id and name?~~ **Settled** — `oliwier.agent-skills-manager`, "Agent Skills Manager". See `DECISIONS.md` D1 for the catalog measurement that chose it.
7. Can you check one row in Claude Code's /plugin browser — does api-design read ~68 or ~85 tokens? I reproduce 68 exactly from round(len(name+description+when_to_use)/4), but one research pass read 85 off your screenshot. If it is 85 the whole token column is ~25% low.
8. Are we targeting a 'passed' marketplace baseline (auto-verified, one-click install)? That forbids any install command anywhere in the repo — including README bash fences outside a ## Development heading and any apt-get in CI — and constrains the upstream-update feature to git fetch with nothing executed from the fetched tree. Your network-usage plugin lost 'passed' to a single 'omarchy pkg add nethogs' README line.

# Blocking gaps
Unknowns that would misdirect implementation if guessed at.
- **OpenCode skill enable/disable cannot be verified after writing. `permission.skill: deny` is confirmed in the binary (`Skill.available` filters on it) and the config plumbing is confirmed live, but no CLI or API surface exposes the filtered set, so the panel cannot render honest OpenCode toggle state or detect that a broader glob overrode a narrow rule.**
  - How to settle: Start `opencode serve` with OPENCODE_CONFIG_CONTENT carrying a deny rule and diff a session's system prompt (or run `opencode run` with a one-word prompt and inspect the <available_skills> block in the session store at ~/.local/share/opencode/opencode.db). ~20 minutes. If unobservable, the honest UI is a write-only toggle labelled 'applies on next opencode restart'.
- **Which file Claude Code's own /skills UI writes, and therefore which file the plugin should write so the two agree. The binary calls it `localSettings`, which resolves to the GIT REPO ROOT's .claude/settings.local.json since 2.1.211 — not the cwd, and not ~/.claude/settings.json. A user-scope write from the panel and a project-scope write from /skills will disagree silently.**
  - How to settle: Toggle one skill off inside /skills in a scratch project and diff which file changed. 10 minutes.
- **Feature 3 (pull upstream updates) has almost no signal for skills. Zero of the 33 unique skill directories is a git repo or inside one; the only origin-ish frontmatter value on the machine is `origin: custom (synthesis)`. The content-hash fallback recovered 32 of 38 in one pass but 29 of those were AMBIGUOUS (multiple candidate upstreams for the same bytes, e.g. n8n skills matching both n8n-mcp-opencode-setup.git and my-omarchy_config.git).**
  - How to settle: Cannot be settled by more research — it is a product decision. Either scope auto-update to Claude plugins + marketplaces only (where gitCommitSha + marketplace repo give an exact answer), or make manual linking the primary path with a plugin-owned sources.json.
- **No write-safety story for opencode.json or ~/.codex/config.toml. Neither has a discoverable lock protocol; opencode rewrites its config while running (an opencode session is live right now, PID 2183445), and config.toml must be CREATED from nothing. There is no comment-preserving TOML writer installed (no tomlkit, tomli-w, taplo, yq, dasel; python3.14 tomllib is read-only).**
  - How to settle: Decide the dependency now: python-tomlkit (Arch extra) plus a bundled span-splice helper, or delegate every Codex write to `codex mcp` / hand-write minimal TOML and accept that comments are not preserved on the file the plugin itself creates.

# Adjudicated contradictions
Where two research passes disagreed, and which one survived scrutiny.
- **What string the clipboard feature must emit for a Claude Code user skill: /taste-skill (directory name) or /design-taste-frontend (frontmatter name)**
  - The Feature-4 topic is WRONG, and dangerously so — following it would make the flagship copy-command feature emit a command that does not exist. For Claude Code user/project skills the invocation, the skillOverrides key and the usage key are all the DIRECTORY name. The frontmatter name is a display label only. (Plugin skills are the exception: /plugin:skill, and skillUsage keys them 'impeccable:impeccable'.) OpenCode and Codex are the mirror image — both key by frontmatter name, which is why OpenCode lists design-taste-frontend and has no taste-skill. Identity must be per-tool; a single skillId field will corrupt state.
  - Evidence: The Feature-4 topic asserts 'The frontmatter name is the identity everywhere (settings key, usage key, slash command)... the user's brief says copy /taste-skill — that is wrong and would paste a command that does not exist.' The Claude Code topic asserts the opposite, citing the docs table (.claude/skills/deploy-staging/SKILL.md -> /deploy-staging) and 'name: is only a display label'. Live evidence I collected: this session's own available-skills listing contains 'taste-skill', not 'design-taste-frontend'; ~/.claude.json skillUsage is keyed 'taste-skill' with 14 uses and has no design-taste-frontend key at all.
- **Whether OpenCode discovers ~/.claude/skills and ~/.agents/skills**
  - OpenCode DOES read both, unconditionally unless OPENCODE_DISABLE_EXTERNAL_SKILLS / OPENCODE_DISABLE_CLAUDE_CODE[_SKILLS] is set. The false negative came from calling GET /api/skill with ?directory=<proj>, which routes to a different, narrower V2 service. Any design premised on 'OpenCode ignores .claude' — including the recommendation to add ~/.agents/skills to skills.paths — is solving a non-problem.
  - Evidence: The OpenCode topic's claim 17 says it did NOT (17/19 skills, all from ~/.config/opencode/skills). Its verifier REFUTED that with a 35-skill listing. The Feature-5 topic repeated the negative claim; its verifier also refuted it. My run: 35 skills — 16 opencode, 13 .claude, 3 .agents, 2 cache, 1 built-in.
- **Whether Claude Code reads ~/.agents/skills**
  - Claude Code does NOT read ~/.agents/skills. ~/.agents is native for Codex, discovered for OpenCode, and reachable for Claude ONLY via symlinks the user placed in ~/.claude/skills. Consequence: 'write once to ~/.agents and all three tools see it' is true for two of three; Claude always needs a symlink or copy. Those symlinks are load-bearing and must never be 'cleaned up' as duplicates.
  - Evidence: Multiple topics treat ~/.agents as the shared cross-tool directory. The Claude Code topic and the OpenCode topic both independently grepped the 2.1.259 binary and found ZERO references to ~/.agents. Codex lists it natively as skill root r1 (I saw it in the roots table from a scratch CODEX_HOME). Claude only sees those skills because ~/.claude/skills/diagnose-crash is an explicit symlink.
- **~/.claude.json top-level mcpServers: 'currently empty' (project brief) vs 'literally null' vs 'absent'**
  - ABSENT. The project brief is wrong. Code doing d['mcpServers'] or assuming {} will behave differently from code doing d.get('mcpServers'). Same for favoritePlugins, which is also absent — so its on-disk shape (array of plugin ids? mixed skill+plugin ids?) remains genuinely unobserved and should not be written blind.
  - Evidence: I loaded the file: 76 top-level keys, 'mcpServers' not among them.
- **skillOverrides precedence: 'local > project > user' vs 'project ?? user, localSettings only as unqualified fallback'**
  - Both descriptions are wrong as descriptions of the gate. The gate reads a merged map in which individual skill keys merge across sources rather than one file replacing another; standard source precedence applies per key, and policy/flag/author/plugin locks sit above all of it. Practical rule for the plugin: compute the effective value from merged settings, show which source supplied it, and write at a level at least as specific as the winning source.
  - Evidence: Binary: the gate is `Sde(e)` reading MERGED settings via Je(): overrides[name] ?? overrides[unqualifiedName] ?? 'on', with bundled-disable and source==='plugin' overrides on top. Separately, skillOverrides is in the per-key merge set with mcpServers/enabledPlugins/env/pluginConfigs. The per-source readers (ho, lm) that both research passes quoted are UI provenance lookups.
- **Whether manifest `activation: "on-demand"` does anything**
  - Decorative. Only top-level `keepLoaded` affects loading. The zero-startup-cost budget must come from declaring kinds:["bar-widget"] only (no "service") and doing literally no work until first open — not from `activation`. Same class of error: manifest barWidget.defaults is never merged into the injected settings, so every default must be a literal in setting(key, fallback).
  - Evidence: The house-style topic recommends it (the user's own opencode-configs plugin sets it) and the architecture topic calls it 'the supported way to avoid startup cost'. The Omarchy API topic says it is decorative. My grep: only two hits under /usr/share/omarchy/shell, both unrelated prose comments.
- **api-design token badge: '~68' vs '~85' in the same screenshot**
  - Unresolved from here — only the user can read the screenshot. The FORMULA is confirmed (round(len(name+' '+description+' '+when_to_use)/4), JS string length, half-up). If the real badge is 85, the formula includes something more and the whole token column is ~25% low; that is worth 30 seconds of the user's time before building the column.
  - Evidence: Two topics say the screenshot shows ~68 (matching the reproducible formula); the UX/IA topic says ~85. I recomputed: 68, and 68 whichever name you use.
- **How slow `opencode mcp list` is (6.1-8.6s vs 5.0-6.5s) and why**
  - The numbers are irrelevant; the cause is decisive. It is a live network round-trip, so it is not merely slow, it is variable and fails offline. Ban it from every interactive path regardless. `codex mcp list --json` (~15-60ms) and `claude plugin list --json` (~0.3s) are fine; opencode data must come from reading opencode.json plus the resolved `opencode debug config`.
  - Evidence: Three independent timing passes disagree on absolute numbers; one verifier found the cause — the command dials every MCP server (output shows '● ✓ websearch connected https://mcp.exa.ai/mcp').
- **Whether <project>/.codex/skills requires the project to be trusted**
  - NOT required. Both <project>/.codex/skills and <project>/.agents/skills were discovered in an untrusted, freshly git-init'd project. Trust gates project CONFIG (including the ignored skills.config), not project SKILL DISCOVERY.
  - Evidence: The Codex topic claims Project-layer skills load only when trusted; its verifier could not reproduce that; I tested directly.
- **Codex [[skills.config]] path selector: skill folder or SKILL.md file**
  - SKILL.md FILE ONLY, absolute. A directory path is accepted by the parser and then silently does nothing — no warning on stdout, skill stays enabled. Prefer the `name` selector, which also survives the skill moving and works for shared ~/.agents skills.
  - Evidence: The Codex topic says 'absolute path to the skill folder or SKILL.md'; its verifier says SKILL.md only. I tested both.
- **How many skills Claude Code sees on this machine (18 vs 16 vs 14)**
  - 16 on-disk-visible, plus roughly 18 bundled ones that no filesystem scan can see. Any 'Claude: N skills' figure and any always-on token total must state which of the two populations it counts, or it will be wrong by about 2x.
  - Evidence: An inventory script counted 18 by wrongly marking the two ~/.agents entries as Claude-visible; the verifier recomputed 16 (14 dirs + 1 symlink in ~/.claude/skills + 1 plugin skill). Separately Claude has ~18 bundled in-binary skills.
- **`claude plugin validate --strict` returning success:true on malformed skills**
  - Both halves matter and only together: the validator IGNORES uppercase names, dir/frontmatter mismatch, 1500-char descriptions, unknown keys, missing name, bogus model and bogus allowed-tools — so it is useless as a portability gate — while --strict fails the whole run on unrelated manifest warnings, so it is also useless as a pass/fail signal. Gate the create form on the Agent Skills spec or Codex's quick_validate.py (the strictest of the three); offer claude plugin validate only as a secondary lint.
  - Evidence: One pass reported success:true with zero warnings on 8 malformed probes; the verifier reproduced the permissiveness but got success:FALSE under --strict (a manifest 'No author information' warning plus the 3 skill warnings each fail the run), and success:true only without --strict.

# Top risks
- **Writing a user's agent config corrupts it. ~/.claude.json is rewritten repeatedly mid-session (measured: five rotated backups at 113/115/144/514-second intervals, inode replaced each time), opencode.json is rewritten with no discoverable lock while a session is live, and ~/.codex/config.toml does not exist so it must be created from nothing with no comment-preserving TOML writer on the machine.**
  - Mitigation: v0.1 writes only ~/.claude/settings.json, opencode.json and a sentinel-delimited block in config.toml, never ~/.claude.json. Every write: prefer the vendor CLI; else span-splice only the key we own; detect-modified-since-read on (mtime_ns,size,inode) and abort on a difference; parse-check the serialised bytes BEFORE the rename; O_EXCL|O_NOFOLLOW temp + fsync + rename + dir-fsync; timestamped backup to our own state dir first, never into ~/.claude/backups which Claude Code prunes to five.
- **QML FileView's write follows symlinks and overwrites the link target — measured in the user's own plugin, with the store landing in an unrelated file every twenty seconds. There is no property that disables it, and several skill paths here are symlinks into /usr/share/omarchy.**
  - Mitigation: Absolute ban on FileView writes. All writes go through the python3 helper's O_EXCL|O_NOFOLLOW temp + rename. FileView is used only as a change SIGNAL on files we watch, and the content is then read through bin/safe-read. A grep assertion in CI fails the build if setText or writeAdapter appears in any .qml.
- **A blocking read or a slow subprocess freezes the entire desktop. omarchy-shell is one process for the whole bar, tray and clock; `opencode mcp list` takes 5-8.6 seconds because it dials every MCP server, a planted FIFO stalls inside open(2) with no descriptor yet to inspect, and a git credential prompt has nowhere to render.**
  - Mitigation: Zero work at shell start; one deferred 5ms summary call at +3s under `timeout 5`. All parsing out of process. O_NONBLOCK on every read so a FIFO returns ENXIO. GIT_TERMINAL_PROMPT=0 and GIT_SSH_COMMAND='ssh -oBatchMode=yes' plus `timeout` on every git call. `opencode` CLI banned from every interactive path — read the resolved config instead. Byte caps agreed at both ends of every pipe.
- **The three tools disagree on skill identity, so one wrong key silently corrupts state or writes a toggle nothing reads. Claude keys by DIRECTORY name, Codex and OpenCode by FRONTMATTER name — ~/.claude/skills/taste-skill declares name: design-taste-frontend and is /taste-skill in Claude but /design-taste-frontend in OpenCode.**
  - Mitigation: Identity is per-tool by construction: every model key is `<tool>:<identity>` with the tool's own rule, `state` and `invocation` are maps rather than scalars, and a rename moves the directory AND edits the frontmatter. The mismatch is itself surfaced as a Needs-attention warning chip, since it makes the skill invalid for OpenCode. A node --test case asserts all three strings for the taste-skill fixture.
- **The classifier is confidently wrong on the user's own data and the taxonomy reads as broken on first open. Measured: api-design lands in `workflow` because it matched the literal word 'design', emil-design-eng lands in `media` at low confidence, taste-skill lands in `web` at medium — three of 36.**
  - Mitigation: Negative rules in the keyword table for `api design`, `schema design`, `database design`, `system design`. Confidence is computed and displayed, `low` and `unclassified` rows sort to the top of their group, and the manual override ships in v0.1 as a single keystroke writing to overrides.json where it is immune to re-detection. marketplace_entry.category is weighted above keywords so the 277 catalog entries that have one are never guessed at.
- **Upstream update detection is unachievable for almost everything installed. Zero of 33 skill directories is a git repo, none of the four skill roots is a repo, /usr/share/omarchy is not a repo, and the only `origin:` field on the machine reads 'custom (synthesis)'. Promising automatic detection would promise something the filesystem cannot support.**
  - Mitigation: Manual linking is designed as the PRIMARY path with a one-paste GitHub tree URL, not as a fallback. Auto-detection is a seven-tier cascade recording which tier fired, with pacman -Qo (on the resolved path, since it fails on the symlink) recovering the Omarchy-packaged skills and the content-hash index recovering 32 more — but that tier is ambiguous for 29 of them, so it presents a menu and never auto-adopts. The whole feature is deferred to v0.3 so v0.1 never ships a dead button.
- **The marketplace rejects the submission or forces manual-setup. The security scanner reads the root README's bash fences AND .github/workflows; a single `omarchy pkg add` line cost this user the package-manager capability before; any file named install/setup/uninstall trips a capability on its name alone; and a git acquisition followed by an execution sink is the blocking remote-git-execution-unpinned finding — which is exactly the shape of the update feature.**
  - Mitigation: Target `passed`: no install command anywhere (anything needed goes under a `## Development` heading, which the scanner skips), no install-named file, no .service, no bundled binary, no apt-get in CI, sys.dont_write_bytecode in the helpers, and 'No sudo or pkexec is required' stated explicitly twice. The update feature is strictly `git -C <dir> fetch/merge` with nothing executed from the pulled tree in the same script — the diff is shown and any build step is the user's to run.
- **Any symlink tracked anywhere in the repository is a hard validation failure, and this plugin's entire subject matter is symlinked skills. `omarchy plugin validate` refuses on the first symlink outside .git, both `plugin add` and `plugin update` call it, and rsync --delete protects an already-deployed excluded name so a stray symlink persists and keeps failing forever.**
  - Mitigation: A `find . -path ./.git -prune -o -type l -print` assertion in CI and in dev-sync.sh, with dev-sync.sh explicitly `rm -rf`ing known tooling paths before the rsync rather than relying on --exclude. Runtime symlink creation (the cross-tool fan-out) is unaffected — the rule is about the repo, not about output — and that distinction is documented in the README.
- **Toggles appear to do nothing. Claude plugin changes need /reload-plugins or a restart; OpenCode never hot-reloads config at all; Codex needs a restart for skills.config; and OpenCode's permission.skill is last-match-wins so a rule written before an existing `*` is silently inert. Users will report all four as bugs.**
  - Mitigation: Every toggle that is not live carries a persistent row note naming the exact action needed. For OpenCode the panel appends its rule and then RECOMPUTES and displays the effective verdict plus the pattern that produced it, rather than echoing back what it wrote. Locked rows (policy, flag, frontmatter disable-model-invocation, plugin-provided) render read-only with the lock reason. A row never draws a switch it cannot honour.
- **A third-party skill description executes or exfiltrates from inside the long-lived shell. Qt's Text defaults to AutoText, which sniffs HTML, so `<img src="https://…">` in arbitrary SKILL.md frontmatter becomes a network fetch made by omarchy-shell; descriptions here run to 950 characters and come from repos nobody audited; and the clipboard feature splices plugin-supplied argument strings into a command the user pastes into a shell.**
  - Mitigation: textFormat: Text.PlainText on every Text, plus a plain() helper that strips <, >, & and zero-width characters before any string reaches a shell component we do not own (PanelHero, Button, ConfirmDialog, PanelToolTip set no textFormat and are not ours to fix). Sanitise once on model ingest, not at each render site. The invocation string is composed only from a validated id plus values drawn from our own parsed enum, newlines stripped, and it stays editable before the copy. Every id-keyed map is Object.create(null) with hasOwnProperty.call lookups, because a skill named __proto__ is possible.
